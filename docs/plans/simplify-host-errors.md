# Host不一致のエラー処理の簡素化

状態：実装済み。既知Host一覧とfallbackの404分類を撤去し、認証ホストの入口を `/` Prefixに統一した。
現在の図は [ルーティング構成](../routing-architecture.md) を参照。

## 固定する要件

1. 公開するHostへの入口がない場合だけ、エラーサービスから421を返す。入口は `/` Prefixに揃え、パス不一致を全体のfallbackで分類しない。
2. 業務アプリの応答ステータス・Content-Type・本文を判定・置換しない。
3. エラー生成は既存SSOポータルに同居し、通常Serviceへ直接転送する。
4. 独立したエラー用Deployment、Kourierの独自ビルド、新しい常駐プロキシは追加しない。
5. 認証用エンドポイントの公開制限は既存の認証処理として維持する。

## 実施内容

### 1. 入口をHost単位に揃える

- 通常アプリは現在の `/` Prefix入口からアプリへ渡す。SSOポータルも同じアプリ扱いとし、専用のHost一致分岐を設けない。
- 認証ホストも `/` Prefixの入口を持たせ、未定義の `/` などを全体のHostエラーへ落とさない。
- 認証入口の公開範囲は維持する。未公開パスは認証入口の404、アプリ固有パスはアプリ自身の404とする。
- 既定の通常・Knative経路、public経路、認証開始・callback・ログアウトを先に確認対象として固定する。

### 2. Kongの404／421分類を削除する

- `known_hosts`／`known_lua` の生成と、`routing-error-reason` のpre-functionを削除する。
- 最後のfallbackは常に `unknown_host` を設定する。
- built-in request-transformerのヘッダー除去・追加で表現し、独自Lua判定を増やさない。
- 元のHost・パス・メソッドを維持し、クライアントのエラー理由・probeヘッダーは信頼しない。

### 3. Kourierとエラー生成サービスを整理する

- Kourierは完全一致するアプリHostを優先し、未一致のwildcardだけエラーサービスへ渡す。
- プロキシからのエラー理由は `unknown_host` のみにする。`path_not_found` との分類は行わない。
- エラーサービスの通常パス不在404は、そのサービス自身の応答として残す。
- `error_service` のname／namespace／portと、同一Podへの同梱・直接Service転送は維持する。
- Knativeのネットワークprobeとhash応答は維持する。

### 4. 受け入れテスト

| ケース | 期待結果 |
| --- | --- |
| 通常アプリが独自JSONで404を返す | 404・Content-Type・本文が完全に維持される |
| Knativeアプリが独自JSONで404を返す | 同上 |
| アプリが421・422・500を返す | エラーサービスへ振り直さず、アプリの応答を維持する |
| エラー生成サービスを停止した状態で業務アプリへ要求する | 業務アプリの200・404は引き続き応答する |
| Kongで未知のHost | 421、Problem Details、リダイレクトなし |
| publicドメイン配下で存在しないKnativeアプリ | 421、Problem Details |
| 既知の認証ホストの未定義パス | 認証入口の404。Hostエラー扱いにしない |
| クライアントが内部エラーヘッダーを付与 | 通常アプリに届かず、fallbackの判定も変えられない |
| Googleログイン・callback・ログアウト | 現行の共有SSOが利用できる |
| Knativeの起動・スケールゼロ復帰 | 新規経路をfallbackと誤認せず正常に復帰する |
| 証明書対象外のHost | TLS検証で失敗する。HTTP処理で証明書エラーを隠さない |

### 検証結果

- Python単体テスト152件成功。実Luaハンドラーの66ケースもこの実行に含む。
- 実Kong・Envoyの結合テスト32ケース成功。アプリ固有JSON・Content-Typeの保持、認証ホストの未定義パス404と公開OAuthパスの転送、エラー生成サービス停止時の影響分離を検証した。
- OAuthの転送先はテスト用アプリ。Googleとの実ログイン、実クラスタのKIC／Knative反映とスケールゼロ復帰は運用環境で確認する。
- 既存の外部確認コマンドは200／アプリ404／未公開Host421を確認する形式のまま使用できる。

## 作業時間を短縮する進め方

- 着手時に変更範囲と受け入れ条件を固定し、追加案は別課題へ分ける。
- 上の1〜3を一つの小さな差分として実装し、設定形式・UI・既存アプリの構成変更を同時に行わない。
- 原則は対象テスト→全体テスト→結合テスト→CIの順に各1回。再実行は変更・失敗があった範囲に限定する。
- 文書だけの変更では全体テストやDockerテストを手元で繰り返さない。
- 開始・設計確定・実装完了・検証完了を時刻付きで記録し、ツールの実行時間と調査・判断の時間を分ける。
- モデル変更の効果は、同程度の作業の総時間と手戻り回数を比較して判断する。モデル名だけを原因と決めない。
